# fleet-guards — сторож нод и сторож трафика для Remnawave

> Впервые? → **[Пошагово с нуля](docs/START-HERE.md)**. Боитесь за работающее? → **[Что сторожа делают и чего не делают](docs/SAFETY.md)**.
> Все флаги, ключи конфига, файлы → **[Справочник](docs/reference.md)**.

Два сторожа, которые читают панель и пишут в Telegram только тогда, когда есть что сказать.
Ничего в панели и на нодах они не меняют.

## node-guard — то, чего панель не видит

Раз в день (и по требованию) проходит по всем нодам:

| проверка | почему панели мало |
|---|---|
| нода отвалилась | это панель видит — включено для полноты картины |
| load на ядро ≥ 0,8 | балансир xray меряет только задержку, про ядра и полосу не знает — перегруз он не предотвратит |
| свободной памяти < 12% | — |
| полоса ≥ 70% от ёмкости канала | ёмкость в панели неизвестна; вы её меряете один раз (`probe-speed.sh` из [node-kit](https://github.com/ponoroshca/remnawave-node-kit)) и записываете в конфиг |
| 🔴 **в маршрутизации моста, но молчит** | ноду заблокировали по IP из страны клиентов: для панели она **жива** — на связи, load 0, трафик 0, ни один порог не превышен. Но она числится в балансире или правиле моста, то есть обязана нести трафик, а несёт ноль, пока остальной флот загружен. Так ловится блокировка, которую иначе замечают через сутки по жалобам |
| цепочка «вход → выход» | на входе люди, выход молчит = разрыв внутри цепочки; обе ноды при этом «здоровы» |

```
Ноды: есть проблемы
🔴 NL-2 (198.51.100.20) — В МАРШРУТИЗАЦИИ (балансир «auto», BRIDGE-NL-IN), НО ТРАФИКА НЕТ (0 юзеров, <1 Мбит),
пока флот несёт 671 Мбит. Похоже на блокировку IP со стороны клиентов. Проверить С МОСТА: …

FI-1               140 Мбит  load 0.91/2я=0.46  ОЗУ своб 76%  юзеров 30 ←в маршруте
NL-2                 0 Мбит  load 0.00/2я=0.00  ОЗУ своб 86%  юзеров 0  ←в маршруте
RF-1               311 Мбит  load 1.10/2я=0.55  ОЗУ своб 41%  юзеров 143
```

Ноды, которые молчат **по вашему решению** (`parked`), в тревогу не попадают — иначе ежедневная
ложная тревога приучает не читать сторожа. Вторые IP нод (`alt_ips`) — чтобы связать outbound
моста с нодой, у которой в панели записан первый адрес.

## traffic-guard — счёт от хостера, до того как он придёт

Лимит трафика у ноды в Remnawave — только уведомление, отсечки нет. А счётчик панели считает
трафик **пользователей**, хостер же выставляет счёт **по интерфейсу** — на 12–15% больше. При квоте
32 ТБ это разница между «всё спокойно» и перерасходом, о котором узнаёшь из счёта.

Сторож раз в 30 минут снимает **сырые счётчики интерфейса** ноды из панели, копит месячный расход
сам (перезагрузки сервера учтены), считает как хостер — `max(вход, выход)` или `вход + выход` — и
сравнивает с включённым объёмом. Пороги 70 / 85 / 95% — **по прогнозу на конец месяца**, чтобы
письмо пришло в начале месяца, когда ещё можно увести трафик, а не 26-го числа. Одно письмо на
порог в месяц; перерасход по прогнозу — отдельным письмом.

```
📊 Трафик ноды: порог 85% по прогнозу
🎯 Нода: RF-1 (203.0.113.10)
📦 Израсходовано: 12.4 ТБ из 32 ТБ (39%)
📈 Прогноз к концу месяца: 27.6 ТБ
💸 Перерасход по прогнозу: 0.0 ТБ
🗓 До сброса счётчика: 17 дн.
```

`traffic-guard --report` — таблица по всем нодам в любой момент.

## Быстрый старт — одна команда

Любой сервер с Python 3.9+ (Ubuntu 22.04/24.04, Debian 12), доступ к панели по сети. Удобно —
тот же сервер, где стоит [bridge-guard](https://github.com/ponoroshca/remnawave-bridge-guard).

```bash
curl -fsSL https://raw.githubusercontent.com/ponoroshca/remnawave-fleet-guards/main/scripts/install.sh | sudo bash
```

Установщик кладёт файлы (не затирая чужие) и открывает мастер: адрес панели и токен → профили
мостов для проверки «молчит» → объём трафика и как его считает хостер → Telegram (получателя
определит сам) → первый отчёт на экран → таймеры. `NO_SETUP=1` — только установить.

```bash
node-guard --force          # отчёт по всем нодам сейчас, в Telegram
traffic-guard --report      # таблица трафика
fleet-guards doctor         # чек-лист «почему не работает»
```

## Что сторожа никогда не делают

Не меняют ничего в панели, на нодах и в DNS; не держат ssh-доступов; знают только API-токен
панели (нужно право чтения) и токен бота. Единственное действие — сообщение в Telegram.
Снять всё: `sudo /opt/fleet-guards/uninstall.sh`. Подробно — [docs/SAFETY.md](docs/SAFETY.md).
